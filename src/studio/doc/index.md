# 量潮组织云工作台

## 定位

组织云的客户端入口，对应「组织云建设意图」（`data/intention/index.md`）的应用层：

> 全平台客户端与命令行并存——「人需要看的内容进客户端」。

工作台本身不持有数据事实。组织数据以 git 仓库为唯一权威源（`data/` 子模块），工作台负责把数据呈现给人、把人的变更写回数据——**数据层与应用层分离**。

**领域边界**：平台聚焦组织本体（蓝图/规则/体检/变革）。入职、离职、交接、权限开通等**人的流程**归人事云；任务节奏、项目状态等**运营管理**归运营域。组织云只消费这些流程产生的**事实**（成员变动、岗位占用），不实现流程本身。

## 背景与动机

组织管理实践中反复出现的四类困难，根因是**组织数据没有权威、可追溯的记录载体**：

1. 信息无权威记录，靠人脑和即时通讯——编制、职责、汇报关系的调整散落在群聊
2. 关键人风险——职责在个人身上，人一走就断
3. 一人多岗导致职责边界模糊——兼任者的归属与边界仅凭记忆维系
4. 信息资产分散、权限靠人肉申请——资料散落孤岛，入职与授权成本高

工作台的目标：让「每次调动的必写处、每次复盘的必读处」有统一、可追溯的载体。

## 模块规划

### 工作台模块（组织本体）

| 意图模块 | 工作台页面 | 关键设计 |
|---|---|---|
| 组织架构模块 | 架构页 | 编制/部门/汇报链路可视化呈现；变更走审批流（写权限受控）；每次调整留版本历史，可追溯 |
| 职责与成员模块 | 成员页 | 每人岗位/汇报对象/兼任实时更新；自动标注单点风险（岗位单人承担、复盘组织者=单人）并提示备选 |
| 组织健康度模块 | 健康度页 | OHI 九维度体检（组织温度计）；复盘为机制健康的数据源，保留独立记录页；体检结论作为「推动变革」的输入 |

### 移出模块（归属其他域）

| 意图模块 | 归属 | 组织云的保留 |
|---|---|---|
| 入职包模块 | 人事云 | 无——入职流程（材料/权限开通）在人事云，组织云不实现 |
| 交接模块 | 人事云 | 仅保留**成员变动影响**事实：岗位空缺、职责悬空、单点风险重算（并入成员页/首页） |
| 时间表模块 | 运营域 | 无——任务节奏管理不在组织本体范围 |
| 状态页 | 运营域 | 无——项目/平台进度管理不在组织本体范围 |

### 边界协议（组织云 ⇄ 人事云）

```
人事云（入职/离职/交接流程）→ 事件 → 数据层事实更新（Member.status、Position 占用）
                                   → 组织云消费事实：岗位空缺、职责悬空、单点风险重算
```

组织云只读事实、展示影响，不参与流程；成员变动的影响视图是组织云的职责（对应「关键人风险」动机）。

## 设计原则

- **数据层与表现层分离**：事实存于 git 仓库（Markdown/结构化文件），工作台只读写同一数据源，不另建事实库
- **变更即提交**：所有写操作落地为数据变更（作者、时间、审批信息随记录留存），天然具备版本历史与审批留痕
- **可回溯**：任何页面呈现的内容都能追溯到数据提交，像代码一样可 diff、可回滚

## 架构分解

应用按 `models/`、`screens/`、`widgets/` 三层分解，遵循单向依赖：`screens → widgets → models`，`models` 零依赖。

```
lib/
├── main.dart                 # 入口：应用装配（主题、路由、导航框架）
├── models/                   # 数据模型（纯数据，不可变，无依赖）
│   ├── org/                  #   组织架构
│   ├── member/               #   成员与职责
│   ├── retrospective/        #   复盘
│   ├── health/               #   组织健康度（OHI 九维度 + 体检报告推导）
│   └── change_record.dart    #   变更记录（通用）
├── screens/                  # 页面（每模块一页，依赖 models + widgets）
│   ├── home/                 #   首页/总览
│   ├── org_structure/        #   架构页（私有组件：DepartmentTree、ChangeHistoryPanel、编制表）
│   ├── members/              #   成员页
│   └── health/               #   健康度页（总览 tab + 复盘记录 tab）
└── widgets/                  # 通用组件（只依赖 models，两页以上复用才提升）
    ├── navigation/           #   导航框架
    ├── data/                 #   数据展示类组件
    └── common/               #   通用基础组件
```

### 数据模型（models/）

模型均为**不可变纯数据**，写操作不直接改模型，而是产生 `ChangeRecord` 提交回数据层。

| 模型 | 意图模块 | 关键字段 | 设计落点 |
|---|---|---|---|
| `Department` | 组织架构 | 名称、上级、负责人 | 编制/归属的唯一权威源 |
| `Position` | 组织架构 | 名称、部门、编制数、状态 | 编制管控：变更走审批流 |
| `ReportRelation` | 组织架构 | 岗位/成员、汇报对象、链路 | 汇报链路可追溯 |
| `Member` | 职责与成员 | 姓名、岗位列表、汇报对象、状态 | 兼任（多岗位）表达，边界显式化；`departed` 触发空缺与风险重算 |
| `Retrospective` | 复盘 | 日程、组织者、参与人、结论 | 组织者=单人时自动标注单点风险；机制健康的数据源 |
| `HealthDimension` | 组织健康度 | 维度、说明、指标、等级 | OHI 九维度之一（McKinsey 框架量潮适配） |
| `HealthReport` | 组织健康度 | 维度列表、整体等级、温度 | 由组织数据推导（`computeHealthReport`），分级约定见 context 手册 |
| `ChangeRecord` | 通用 | 作者、时间、审批、提交 ID、变更内容 | 变更即提交：留痕与回溯 |

> 精简说明：不设容器/子模型（版本由 `ChangeRecord` 链推导，任职内嵌于 `Member`）；入职包、交接、时间表、状态页模型随模块移出。每个模型的字段定义、规则与示例数据见 [models.md](./models.md)。

### 页面（screens/）

| 页面 | 对应模块 | 核心功能 | 关键设计落点 |
|---|---|---|---|
| `HomeScreen` | — | 工作台总览：待审批变更、单点风险、岗位空缺聚合 | 组织风险在首页聚合展示（必读处） |
| `OrgStructureScreen` | 组织架构 | 架构图浏览（编制/部门/汇报链路）；变更入口 | 变更落 `ChangeRecord`（审批流在数据层）；版本历史可追溯 |
| `MembersScreen` | 职责与成员 | 成员列表与详情（岗位/汇报/兼任）；成员变动影响 | 单点风险标注并提示备选；`departed` 成员的岗位空缺/职责悬空展示 |
| `HealthScreen` | 组织健康度 | 总览 tab：组织温度计 + OHI 九维度；复盘记录 tab：日程/结论/状态流转 | 复盘是机制健康数据源；体检结论作为「推动变革」输入 |

> 每个页面的布局结构、关键交互与状态设计见 [screens.md](./screens.md)。

### 通用组件（widgets/）

跨页面复用的组件集中于此；页面私有的组件留在对应 `screens/<page>/` 子目录。

| 分类 | 组件 | 用途 | 使用页面 |
|---|---|---|---|
| `navigation/` | `AppShell` | 侧边栏/导航栏：四个页面入口 | 全部页面 |
| `data/` | `MemberCard` | 成员信息卡（岗位/汇报/兼任） | 成员页、健康度页 |
| `data/` | `StatusBadge` | 状态徽章（正常/风险/待审批） | 首页、成员页、健康度页 |
| `common/` | `RiskBadge` | 单点风险标注（岗位单人/复盘组织者=单人） | 首页、成员页、健康度页 |
| `common/` | `EmptyState` | 空态：无数据时的引导 | 全部页面 |

> 精简说明：`DepartmentTree`、`ChangeHistoryPanel`、编制表随状态页/时间表移除后仅架构页使用，按复用规则降级为架构页私有组件。每个组件的属性、行为与使用场景见 [widgets.md](./widgets.md)。

## 数据流与依赖规则

```
数据层（git 仓库） ⇄ models（纯数据） ⇄ screens（页面） ⇄ widgets（通用组件）
```

- **单向依赖**：`screens → widgets → models`；`models` 无任何依赖（纯数据类）
- **写操作路径**：页面交互 → 构造变更（`ChangeRecord`）→ 提交到数据层，模型本身不可变
- **读操作路径**：数据层加载 → 模型实例 → 页面/组件渲染
- 页面私有组件不进 `widgets/`；两个以上页面复用才提升到 `widgets/`

## 建设路径

| 阶段 | 内容 | 原则 |
|---|---|---|
| 一、原型 | 参照成熟产品形态快速实现第一个可用原型，先上线小范围使用 | 产品负责「好用」，技术负责「能用」 |
| 二、迭代 | 按真实使用反馈补齐模块，逐步覆盖架构/成员/健康度 | 习惯优先于工具——先建立记录与复盘的习惯，再谈自动化 |
| 三、工具化 | 习惯稳定后，将重复操作自动化；与数据层工具链（git 命令行）互补并存 | 工具是习惯的载体，不是替代品 |

### 原型阶段落地（阶段一）

原型阶段只实现 `HomeScreen` 导航框架（`AppShell`）+ 各页空态壳（`EmptyState`），数据用内存中的 8 个示例模型跑通渲染，不接数据层读写；核心组件只用 `RiskBadge` / `StatusBadge` / `EmptyState` 三个，其余按需从页面私有组件提升；页面逐个按模块规划填充。
